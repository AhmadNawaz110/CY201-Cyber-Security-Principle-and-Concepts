1. Cloud Fundamentals & Architecture
Beginner
Learning Objectives (Bloom's: Understand) Define NIST Service/Deployment models and articulate the Shared Responsibility Model boundaries.

Service Models (SPI)

  • IaaS: Infrastructure as a Service. Provider manages hardware/virtualization. User manages OS, apps, data. (e.g., AWS EC2, Azure VM).
  • PaaS: Platform as a Service. Provider manages OS/Runtime. User manages Data/Apps. (e.g., Google App Engine, Azure SQL).
  • SaaS: Software as a Service. Provider manages everything. User manages access/usage. (e.g., Salesforce, Office 365).

Deployment Models

  • Public: Shared infrastructure, open to general public.
  • Private: Exclusive use by one organization (on-prem or cloud).
  • Hybrid: Composition of two or more models bound by technology.
  • Multi-cloud: Using services from multiple cloud providers (e.g., AWS + Azure).

Case Study: The Capital One Breach (2019)

Scenario: A former AWS employee exploited a Server-Side Request Forgery (SSRF) vulnerability in a Web Application Firewall (WAF) misconfiguration.

Technical Failure: The WAF was allowed to query the EC2 Instance Metadata Service (IMDSv1), which exposed temporary credentials. These credentials had excessive permissions (IAM Role) allowing access to S3 buckets.

Mitigation: Migration to IMDSv2 (session-oriented), enforcing strict IAM policies, and restricting WAF outbound connectivity.

2. Identity & Access Management (IAM)
Intermediate
Learning Objectives (Bloom's: Apply) Design Least Privilege policies and distinguish between Authentication and Authorization.

Core IAM Concepts

  • Principal: An entity authenticated by AWS (User, Role, Federated User).
  • Request: Principals send requests to AWS services.
  • Authentication (AuthN): Verify identity (MFA, SSO, Federation).
  • Authorization (AuthZ): Verify permissions (Policy evaluation logic).

Policy Evaluation Logic

1. Default Deny: All requests are denied by default.
2. Explicit Allow: If any policy allows, check for explicit deny.
3. Explicit Deny: Overrides any allow.

Secure vs. Insecure Code

Scenario: An EC2 instance needs to read objects from a specific S3 bucket.

❌ Insecure: Hardcoded Keys

// In application code (e.g., Python) conn = boto3.client('s3', aws_access_key_id='AKIA...', aws_secret_access_key='l0ngStr1ng...' )

✅ Secure: IAM Role (Instance Profile)

// In application code // No keys needed! conn = boto3.client('s3') # Permission comes from the attached IAM Role

3. Data Security & Encryption
Intermediate
Learning Objectives (Bloom's: Analyze) Compare Client-Side vs. Server-Side encryption and explain Key Management hierarchy.

Encryption States

  • At Rest: Data stored on disks (EBS, S3, RDS). Standard: AES-256.
  • In Transit: Data moving over network (TLS 1.2+).

Key Management

  • CMEK (Customer Managed Keys): You control the key lifecycle (KMS).
  • BYOK (Bring Your Own Key): Key material generated outside cloud and imported.

Envelope Encryption

Encrypting a data key with a master key. This allows performance (data key does the heavy lifting) and security (master key is stored in HSM).

Scenario: Financial Services (PCI-DSS)

A bank is migrating credit card data to the cloud. Compliance requires that the Cloud Provider cannot access the raw data.

Solution: Use Client-Side Encryption. The bank encrypts data locally before uploading to S3. The Cloud Provider only sees ciphertext.

4. Cloud Network Security
Intermediate

VPC Components

  • VPC: Isolated network boundary.
  • Subnet: Range of IP addresses. Public (IGW route) vs Private.
  • Route Table: Maps network traffic (destinations).
  • Security Group (SG): Stateful firewall at instance level.
  • NACL: Stateless firewall at subnet level.

5. Cloud Threat Modeling & MITRE ATT&CK
Advanced
Learning Objectives (Bloom's: Evaluate) Apply STRIDE methodology to cloud architectures and map tactics to MITRE ATT&CK Cloud matrix.

STRIDE Methodology

  • Spoofing: Impersonating a user or process (e.g., Stolen IAM Keys).
  • Tampering: Modifying data (e.g., altering S3 object).
  • Repudiation: Denying an action (e.g., CloudTrail logging disabled).
  • Information Disclosure: Data leak (e.g., Public S3).
  • Denial of Service: Exhausting resources (e.g., Lambda throttling).
  • Elevation of Privilege: Gaining higher access (e.g., IAM CreatePolicyVersion).

Attack Scenario: PrivEsc via IAM

Tactic: Privilege Escalation (T1489 or similar).
Technique: An attacker creates a new version of an existing policy attached to their user, changing "Allow" to "*". They then detach the old version.

6. Governance, Risk & Compliance (GRC)
Advanced

Key Frameworks

  • NIST SP 800-53: Catalog of security controls for US Fed systems.
  • ISO 27001: International standard for ISMS.
  • CIS Benchmarks: Configuration guidelines (e.g., "Ensure S3 buckets are not public").
  • CSA CCM: Cloud Controls Matrix.

Continuous Compliance

Manual audits are too slow. Use Configuration Rules (e.g., AWS Config, Azure Policy) to detect drift in real-time.

# Example Rule: S3 Public Read Prohibited if s3_bucket.acl.grants == 'AllUsers' { return NON_COMPLIANT }
