NIST Essential Characteristics
Beginner
Objective: Define the 5 essential characteristics of Cloud Computing (NIST).
  • On-demand self-service: A consumer can unilaterally provision computing capabilities without human interaction with the service provider.
  • Broad network access: Capabilities are available over the network and accessed through standard mechanisms.
  • Resource pooling: The provider’s computing resources are pooled to serve multiple consumers using a multi-tenant model.
  • Rapid elasticity: Capabilities can be elastically provisioned and released, in some cases automatically, to scale rapidly with demand.
  • Measured service: Resource usage can be monitored, controlled, and reported, providing transparency for both the provider and consumer.
Service Models Deep Dive
Beginner

Infrastructure as a Service (IaaS)

Provides virtualized computing resources over the internet.

  • You manage: OS, Middleware, Runtime, Data, Applications.
  • Provider manages: Network, Storage, Servers, Virtualization.
  • Examples: AWS EC2, Azure Virtual Machines, Google Compute Engine.
  • Use Case: Lift and Shift migrations, dev/test environments.

Platform as a Service (PaaS)

Hardware and software tools available over the internet.

  • You manage: Applications, Data.
  • Provider manages: OS, Middleware, Runtime, Virtualization, Servers, Storage, Networking.
  • Examples: AWS Elastic Beanstalk, Google App Engine, Azure App Service.
  • Use Case: Developers focusing on code without managing infrastructure.

Software as a Service (SaaS)

Software licensed on a subscription basis.

  • You manage: None (specific configurations/access rights only).
  • Provider manages: Everything (App to Network).
  • Examples: Microsoft 365, Salesforce, Dropbox, Gmail.
  • Use Case: End-user productivity, CRM, Email.
Deployment Models
Beginner

Public Cloud

Owned by a third-party cloud service provider. Hardware is shared.

Pros: No capex, high scalability, Cons: Limited customization, shared tenancy risks.

Private Cloud

Used exclusively by one organization. Can be on-prem or hosted.

Pros: Maximum control, compliance, Cons: High cost, maintenance burden.

Hybrid Cloud

Combines public and private clouds, bound by technology.

Key: Portability of data and apps (e.g., Cloud bursting).

Multi-Cloud

Using services from multiple public cloud providers (AWS + Azure).

Risk: Complexity in IAM and Networking.

Installed directly on hardware. No underlying OS. High performance.

Shared Responsibility Model (SRM)
Beginner
Objective: Distinguish between "Security OF the Cloud" and "Security IN the Cloud".

Provider Responsibility

Security OF the Cloud:

  • Physical security of data centers.
  • Hardware maintenance.
  • Network core infrastructure.
  • Hypervisor patching.

Customer Responsibility

Security IN the Cloud:

  • Data classification.
  • Identity & Access Management (IAM).
  • OS patching (IaaS).
  • Network configuration (VPC, Firewalls).
Real World Impact: In the 2019 Capital One breach, AWS secured the infrastructure (Provider), but Capital One was responsible for configuring the WAF and IAM policies (Customer). The failure occurred in the Customer's layer.
IAM: Core Concepts
Intermediate

Principal

An entity that can be authenticated and authorized to perform actions.

  • Root User (Master)
  • IAM User (Human)
  • IAM Role (Service)
  • Federated User (External IdP)

Request

A request is sent by a Principal to AWS.

  • Context: Source IP, Time, Date.
  • Auth Info: Credentials (Keys, Session).
  • Action: e.g., s3:ListBucket.

Authentication (AuthN)

Verifying WHO you are.

  • Console Password
  • Access Keys (CLI/SDK)
  • MFA (Multi-Factor Auth)
Authentication Mechanisms
Intermediate

Multi-Factor Authentication (MFA)

Requires two distinct factors: Something you know (password) and Something you have (device/token).

Best practice: Enforce MFA on the Root account and all IAM users.

Industry: Virtual MFA (Google Authenticator) vs Hardware MFA (YubiKey). Hardware is phishing-resistant.

Federation (SAML 2.0)

Allows users to authenticate with corporate Active Directory and access AWS without creating IAM users.

  • IdP: Identity Provider (Corporate AD).
  • SP: Service Provider (AWS).
  • Trust is established via metadata exchange.

Web Identity (OIDC / OAuth 2.0)

Authentication via external identity providers like Google, Facebook, or Amazon Cognito.

Commonly used for mobile apps and web applications where users don't have corporate accounts.

Authorization (AuthZ) Logic
Intermediate
Objective: Understand the Default Deny stance.

Evaluation Order

  1. Default Deny: Everything is denied by default.
  2. Explicit Allow: Check all policies (Identity-based, Resource-based) for an "Allow".
  3. Explicit Deny: Check for a "Deny". Deny overrides Allow.
Scenario: User has an "Allow S3 Read" policy, but the S3 Bucket Policy has a "Deny All from VPC X" and the user is in VPC X.
Result: Access Denied.
IAM Policy Structure (JSON)
Intermediate

Policy Elements

  • Version: Policy language version (e.g., "2012-10-17").
  • Statement: The core block. Can contain multiple statements.
  • Sid: Optional statement ID.
  • Effect: "Allow" or "Deny".
  • Action: Specific API call (e.g., "s3:GetObject").
  • Resource: ARN of the target (e.g., "arn:aws:s3:::bucket/*").
  • Condition: Optional constraints (e.g., IP address, Time).

Example Policy

{ "Version": "2012-10-17", "Statement": [ { "Effect": "Allow", "Action": "s3:ListBucket", "Resource": "arn:aws:s3:::my-app-bucket", "Condition": { "IpAddress": { "aws:SourceIp": "203.0.113.0/24" } } } ] }
Least Privilege & Boundaries
Intermediate

Principle of Least Privilege (PoLP)

Only grant the permissions required to perform a task. Start with no permissions and add only what is needed.

Permissions Boundaries

A managed policy that sets the maximum permissions that an entity-based policy can grant to an IAM entity.

Useful for delegating IAM creation to developers without giving them Admin rights.

SCP (Service Control Policies)

Used in AWS Organizations. They define the guardrails for ALL accounts in an OU.

Example: "Deny access to us-east-1 region for the entire organization."

IAM Federation & Roles
Intermediate

Why Roles?

Roles are not associated with a specific user or group. Instead, trusted entities assume roles.

  • EC2 Instance Profile: App on EC2 needs S3 access. Don't embed keys. Use a Role.
  • Cross-Account Access: Account A trusts Account B to assume a Role.

Encryption: Symmetric vs Asymmetric
Intermediate

Symmetric Encryption

Uses a single key for both encryption and decryption.

  • Algorithms: AES (Advanced Encryption Standard) - AES256.
  • Pros: Fast, efficient for large data (Databases, S3 objects).
  • Cons: Key distribution problem (how to share the key securely).

Asymmetric Encryption

Uses a Key Pair: Public Key (encrypt) and Private Key (decrypt).

  • Algorithms: RSA, ECC (Elliptic Curve).
  • Pros: Solves key distribution, enables digital signatures.
  • Cons: Computationally expensive. Used for small data (keys, secrets).

Data at Rest & KMS
Intermediate

Envelope Encryption

Uses AWS KMS (Key Management Service) to encrypt the Data Key, which encrypts the Data.

Key Options

  • SSE-S3: Keys managed by S3.
  • SSE-KMS: Keys managed by KMS (Auditable, Rotation support).
  • SSE-C: Customer provides key (per request).
  • Client-Side: Encrypt before uploading.
Data in Transit
Intermediate

TLS / SSL

Transport Layer Security ensures data traveling over the network is encrypted.

SSL Termination

Where the decryption happens.

  • At Load Balancer: LB handles SSL. Backend traffic is HTTP (internal network). Easier for LB, but backend must be secured.
  • At Backend: Pass-through. Traffic stays HTTPS all the way to the server. More secure, higher CPU load on servers.

Best Practices

  • Enforce HTTPS only (redirect HTTP).
  • Use modern TLS versions (1.2+).
  • Use strong Ciphers.
  • Certificate management (ACM / Certificate Manager).
Network: VPC Fundamentals
Intermediate
Objective: Construct a secure VPC with public and private subnets.
  • VPC (Virtual Private Cloud): Isolated network in the cloud.
  • Subnet: Range of IPs in the VPC.
  • CIDR: Classless Inter-Domain Routing (e.g., 10.0.0.0/16).
  • Route Table: Rules for where network traffic is directed.
  • IGW (Internet Gateway): Allows communication between VPC and Internet.
Security Design: Never place databases in a public subnet. Databases should reside in private subnets with no direct route to an IGW.

Hybrid Cloud Connectivity
Advanced

Site-to-Site VPN

Encrypted connection over the public Internet.

  • Pros: Low cost, easy setup.
  • Cons: Variable latency, reliant on internet bandwidth.

AWS Direct Connect / Azure ExpressRoute

Dedicated physical fiber connection.

  • Pros: Consistent latency, higher bandwidth, more secure (no public internet).
  • Cons: Higher cost, longer lead time.
Industry Scenario: A hospital requires real-time access to cloud-based MRI archives. They choose Direct Connect to ensure low latency and reliability, critical for patient care.
Compute: VM Security
Intermediate

EC2 / VM Hardening

  • AMIs: Use trusted, hardened images. Scan for vulnerabilities.
  • User Data: NEVER pass secrets (passwords/keys) in User Data scripts. They are visible in the console.
  • SSM (Systems Manager): Use Session Manager for shell access instead of opening SSH (Port 22).
  • Patching: Automate OS patching using Systems Manager Patch Manager.

Container Security (Docker)
Advanced

Container Threats

  • Vulnerable Images: Base OS with known CVEs.
  • Secrets in Code: API keys hardcoded in Dockerfile.
  • Privileged Mode: Running as root gives access to host kernel.

Best Practices

  • Immutable Infrastructure: Don't patch containers; rebuild and redeploy.
  • Scan Images: Use Trivy, Clair, or ECR Scan.
  • Minimize Layers: Reduce attack surface.
  • Run as Non-Root: Use `USER` directive in Dockerfile.
Kubernetes (K8s) Security
Advanced

The 4 C's of Cloud Native Security

  1. Cloud: VPC, IAM (Underlying infra).
  2. Cluster: Control plane components, API Server, Etcd encryption.
  3. Container: Image scanning, run as non-root.
  4. Code: App security.

K8s Controls

  • Pod Security Policies (PSP) / Pod Security Standards: Control what pods can do (privilege escalation, host networking).
  • Network Policies: K8s firewall (allow pod A to talk to pod B).
  • Service Accounts: Identity for pods (IRSA).
Logging Strategy
Intermediate

AWS CloudTrail

Records API calls made in your account.

  • Management Events: CreateBucket, RunInstances (Control Plane).
  • Data Events: GetObject, DeleteObject (Data Plane - cost money).
  • Deliver to S3 for long-term storage.

VPC Flow Logs

Information about the IP traffic going to and from network interfaces.

  • Source/Dest IP, Ports, Protocol, Bytes.
  • Useful for forensics and network debugging.
CloudTrail Log Analysis
Intermediate

What to look for in logs?

  • Unauthorized Access: `ConsoleLogin` from MFA=No or unusual SourceIP.
  • Privilege Escalation: `CreatePolicyVersion`, `AttachUserPolicy`, `PutBucketPolicy`.
  • Defense Evasion: `StopLogging` (CloudTrail), `DeleteTrail`.
  • Crypto Mining: Unusual `RunInstances` with spot instances.
Scenario: Alert triggers on `CreateAccessKey` for a user that hasn't been active in 6 months. Action: Investigate immediately for compromise.
Cloud Incident Response
Advanced

NIST Phases

1. Preparation

Playbooks, Monitoring alerts, IAM roles for IR team.

2. Detection & Analysis

CloudWatch Alarms, GuardDuty findings, VPC Flow Logs analysis.

3. Containment

Detach IAM role, Revoke keys, Isolate instance (Security Group deny all).

4. Eradication

Terminate malicious instances, Patch vulnerabilities.

5. Recovery

Restore from clean backups, Verify system integrity.

6. Post-Incident

Lessons learned, update runbooks.

OWASP Cloud Top 10
Advanced
  1. Injection: SQL injection in cloud apps.
  2. Broken Authentication: Weak passwords, session management.
  3. Sensitive Data Exposure: Unencrypted S3 buckets.
  4. XML External Entities (XXE): XML processor vulnerabilities.
  5. Broken Access Control: IDOR (Insecure Direct Object References).
  6. Security Misconfiguration: Open Security Groups, default keys.
  7. Cross-Site Scripting (XSS): Client-side scripts.
  8. Insecure Deserialization: Remote code execution.
  9. Using Components with Known Vulnerabilities: Old libraries.
  10. Insufficient Logging & Monitoring: No audit trail.
